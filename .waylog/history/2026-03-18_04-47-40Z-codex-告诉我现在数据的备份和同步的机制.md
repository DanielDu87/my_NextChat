数据备份由本地 IndexedDB 作工作副本、PostgreSQL 作为云端可信副本的“本地优先”架构承担：所有对话、插件、设置、Prompt/Mask、模型配置、更新状态和绘图记录等关键数据都先写入 IndexedDB，后台通过 `sync_artifacts` 表保留云端快照，页面加载时先读本地再比对 `updatedAt/checksum`，若云端版本变动且本地无未同步记录就从数据库下载并刷新本地；云端版本一致则只做元信息检查，避免重复下载。`docs/db/data-storage-sync-matrix.md` 展示了各类数据的存储位置、读取策略和同步行为，`docs/db/local-first-sync-rules.md` 说明了冲突判定、手动操作（“保存并同步”上传并更新版本、“上传到数据库”仅上传、“从数据库下载”强制覆盖）以及自动同步触发点。

同步流程通过 `auto-sync` 组件在页面加载时驱动一次 `syncStore.sync()`：先完成本地优先展示再在后台根据前述策略进行双向合并或单向覆盖，出现本地/云端同时发生更新的情况会标记冲突而不自动覆盖。模型相关数据则依赖后台脚本或受控接口同步供应商 API，再写入 `model_catalog` 和相关 `sync_artifacts`，前端下一次检测到版本差异时再按需合并。整个机制只对业务数据进行云端备份，UI 偏好字段（如 `sidebarWidth`、语言、草稿）仅保留本地，不参与同步。

建议你按需要进一步：1. 检查 `docs/db/data-storage-sync-matrix.md` 了解每类数据的备份/同步行为；2. 在界面上使用“保存并同步”或“从数据库下载”来验证本地与 PostgreSQL 的双向同步。

**机制总览**

现在这套数据机制不是“单纯备份”，而是“本地优先 + 云端快照 + 按版本校验同步”。

可以直接理解成三层：

| 层级 | 作用 | 存什么 | 是否参与同步 |
| --- | --- | --- | --- |
| 本地 `IndexedDB` | 日常工作副本，页面优先读取 | 对话、插件、设置、Prompt、Mask、模型配置、更新状态、绘图记录、同步状态 | 是 |
| 本地 `localStorage` | 纯 UI 偏好和临时态 | 侧边栏宽度、语言、横幅关闭状态、输入草稿 | 否 |
| 云端 `PostgreSQL` | 共享副本、备份副本、最终可信源 | 各类业务数据快照、模型目录、同步元数据 | 是 |

这点在 [data-storage-sync-matrix.md](/Users/dyx/Code/NextChat/docs/db/data-storage-sync-matrix.md) 和 [local-first-sync-rules.md](/Users/dyx/Code/NextChat/docs/db/local-first-sync-rules.md) 里写得比较明确。

会进云端备份的核心数据如下：

| --- | --- | --- | --- |
| 对话数据 | `chat-next-web-store` | `sync_artifacts` | 聊天记录主体 |
| 插件数据 | `chat-next-web-plugin` | `sync_artifacts` | 插件配置与状态 |
| API / 平台配置 | `access-control` | `sync_artifacts` | 各平台 profile、密钥相关配置 |
| 模型配置 / 缓存 | `app-config` | `sync_artifacts` | 前端看到的模型列表和设置 |
| Mask | `mask-store` | `sync_artifacts` | 面具数据 |
| Prompt | `prompt-store` | `sync_artifacts` | 提示词数据 |
| 更新状态 | `chat-update` | `sync_artifacts` | 更新检查相关状态 |
| 绘图记录 | `sd-list` | `sync_artifacts` | 绘图历史 |
| 同步元信息 | `sync` | 本地为主，云端可选快照 | 用来记录同步状态和版本信息 |
| 模型目录主表 | 无直接本地整表 | `model_catalog` | 服务端维护的模型目录 |
| 模型同步记录 | 无 | `model_sync_runs` | 记录模型刷新任务 |

| 横幅关闭状态 | `localStorage` | 临时 UI 状态 |
| 输入草稿 | `localStorage` | 临时内容，避免污染云端 |

---

**页面打开时怎么同步**

页面不是一上来就从数据库全量拉取，而是先读本地，再做轻量检查。

| 阶段 | 行为 | 目的 |
| --- | --- | --- |
| 1 | 先读 `IndexedDB` | 立即渲染，保证打开页面快 |
| 2 | 后台请求云端元信息 | 只检查版本是否变化 |
| 3 | 比较本地与云端的 `updatedAt/checksum/sizeBytes` | 判断是否真的有更新 |
| 4 | 若云端变了且本地没脏数据，则下载云端正文 | 用云端刷新本地 |
| 5 | 若云端变了且本地也改过，则标记冲突 | 不自动覆盖，避免丢数据 |

相关规则见 [local-first-sync-rules.md](/Users/dyx/Code/NextChat/docs/db/local-first-sync-rules.md)；元信息来源接口在 [route.ts](/Users/dyx/Code/NextChat/app/api/db/sync-meta/route.ts)。

也就是说，这里不是“每次打开都把数据库覆盖本地”，而是：

- 本地永远先展示
- 云端只先检查“版本”
- 真有必要才下载正文
- 本地有未同步修改时，不静默覆盖

---

**自动同步怎么触发**

自动同步由前端组件驱动，不是用户每次都得手动点按钮。

| 触发点 | 行为 |
| --- | --- |
| 页面加载 | 调用 `syncStore.sync()` |
| 自动同步过程 | 先本地渲染，再按规则尝试合并 / 上传 / 校验 |
| 自动同步范围 | 当前相关业务 store |
| 自动同步目的 | 让本地和云端尽量保持一致，但不牺牲本地优先和安全性 |

这个逻辑在 [auto-sync.tsx](/Users/dyx/Code/NextChat/app/components/auto-sync.tsx) 和 [sync.ts](/Users/dyx/Code/NextChat/app/store/sync.ts) 里。

简化理解：

| 场景 | 自动行为 |
| --- | --- |
| 本地没改，云端变了 | 自动下载云端 |
| 本地改了，云端没变 | 自动可上传或保持待同步状态 |
| 本地和云端都改了 | 标记冲突，不自动强覆盖 |

**手动按钮分别是什么意思**

这个系统里，手动动作的语义很明确，不同按钮代表不同数据方向。

| 操作 | 本地数据 | 云端数据 | 结果 |
| --- | --- | --- | --- |
| `保存并同步` | 作为源数据 | 被本地覆盖或参与合并 | 上传后刷新本地记录的云端版本信息 |
| `上传到数据库` | 作为源数据 | 被本地覆盖 | 只上传，不下载 |
| `从数据库下载` | 被云端覆盖 | 作为源数据 | 强制用云端覆盖本地 |
| 页面自动校验 | 先本地渲染 | 只检查版本 | 仅在需要时下载正文 |

这张表就在 [data-storage-sync-matrix.md](/Users/dyx/Code/NextChat/docs/db/data-storage-sync-matrix.md)。

---

**不同数据的合并策略不一样**

这套系统不是所有数据都粗暴“本地覆盖云端”，而是按数据类型处理。

| 数据类型 | `保存并同步` 时策略 | 原因 |
| --- | --- | --- |
| 对话数据 | 双向合并 | 避免覆盖历史会话和消息 |
| 插件数据 | 双向合并 | 按插件 key 合并更安全 |
| API Profiles | 双向合并 | 多端 profile 可能分别新增 |
| 模型集合 | 双向合并 | 按 `model.name + provider.id` 合并 |
| Prompt | 双向合并 | 避免不同端新增丢失 |
| Mask | 双向合并 | 同上 |
| 绘图记录 | 双向合并 | 历史记录天然适合追加式合并 |
| 页面主设置 | 本地覆盖云端 | 当前设备显式保存的设置优先 |
| 派生字段 `cachedModels` / `modelCount` | 云端覆盖本地 | 这些是服务端刷新出来的派生结果 |
| 更新状态 `chat-update` | 云端覆盖本地 | 控制面状态不做复杂 merge |
| 同步元信息 `sync` | 云端覆盖本地 | 版本状态以校验结果为准 |
| `sidebarWidth/lang/草稿` | 不同步 | 纯本地 |

这部分定义在 [data-storage-sync-matrix.md](/Users/dyx/Code/NextChat/docs/db/data-storage-sync-matrix.md) 3.1 节。

核心原则其实是：

- “历史型、集合型”数据用双向合并
- “控制型、派生型”数据用单向覆盖
- “纯 UI”数据不进云端

---

**云端怎么判断有没有变化**

同步时不会直接比较整个对象，而是先看元信息。

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `updatedAt` | `sync_artifacts.updated_at` | 判断云端是否更新过 |
| `checksum` | `md5(payload_json::text)` | 判断内容是否真的变化 |
| `sizeBytes` | `pg_column_size(payload_json)` | 辅助日志和诊断 |
| `validatedAt` | 本地 `sync.database.cacheMeta` | 记录最近一次校验时间 |

这样做的好处：

- 页面快，不需要每次全量下载
- 内容没变时不会重复同步
- 能区分“时间变了但内容没变”和“内容确实变了”

---

**冲突时怎么处理**

这部分非常关键：当前机制明确偏保守，不做激进的自动三方合并。

| 场景 | 处理方式 |
| --- | --- |
| 云端变化，本地没改 | 下载云端覆盖本地 |
| 本地变化，云端没改 | 以上传本地为主 |
| 本地和云端都变了 | 标记冲突，不静默覆盖 |
| 模型 / 设置冲突 | 默认按按钮语义处理，不做复杂三方 merge |
| 会话同时变化 | 不自动静默覆盖，后续应让用户选上传本地还是下载云端 |

也就是说，目前系统的设计目标是“宁可多一步确认，也不要丢数据”。

---

**模型数据的同步是另一条链路**

模型不是页面直接请求供应商 API 拿来当主数据源，而是后台先拉，再写云端，前端只同步结果。

| 环节 | 来源 | 写入位置 |
| --- | --- | --- |
| 供应商模型拉取 | 各 provider API | 内存归一化结果 |
| 归一化处理 | 服务端拉取器 | `SyncedLLMModel[]` |
| 模型目录持久化 | 归一化结果 | PostgreSQL `model_catalog` |
| 前端模型快照更新 | 同一批结果 | `sync_artifacts.app-config` |
| 前端 profile 缓存更新 | 同一批结果 | `sync_artifacts.access-control` |
| 页面本地更新 | 下次版本校验发现变更 | `IndexedDB` |

相关实现文件：

- [provider-model-fetch.ts](/Users/dyx/Code/NextChat/app/utils/server/provider-model-fetch.ts)
- [provider-model-sync.ts](/Users/dyx/Code/NextChat/app/utils/server/provider-model-sync.ts)
- [refresh-provider-models.ts](/Users/dyx/Code/NextChat/scripts/refresh-provider-models.ts)
- [route.ts](/Users/dyx/Code/NextChat/app/api/db/models/refresh/route.ts)

这意味着：

- 页面加载时不会直接打供应商接口
- 供应商 API 只是“更新来源”
- 真正参与前端同步的是数据库里的模型快照

---

**你可以怎么理解“备份”和“同步”**

如果严格区分：

| 概念 | 在当前系统里的含义 |
| --- | --- |
| 备份 | PostgreSQL 保存了一份本地业务数据的云端快照 |
| 同步 | 本地 `IndexedDB` 和云端 `PostgreSQL` 按版本规则双向对齐 |
| 自动同步 | 页面加载后自动做版本校验和必要的合并/下载 |
| 手动同步 | 用户主动点按钮决定上传、下载或保存并同步 |
| 最终可信源 | 云端 PostgreSQL，但页面体验仍然本地优先 |

所以它不是传统意义上的“定时全量备份系统”，而是：

- 平时以本地为工作区
- 云端保存可恢复快照
- 通过元信息判断是否同步
- 对高风险冲突保持保守策略

---

**一句话总结**

当前机制是“`IndexedDB` 本地优先工作副本 + `PostgreSQL` 云端快照备份 + 基于 `updatedAt/checksum` 的按需同步”，其中聊天、设置、插件、Prompt、Mask、模型配置等核心业务数据都参与备份与同步，纯 UI 偏好不参与；自动同步负责页面加载后的轻量校验和安全合并，手动按钮负责显式上传或下载，冲突时默认不自动覆盖。

模型缓存是什么作用


## 🤖 Assistant (2026-03-18 05:05:53 UTC)

模型缓存的作用，核心就是一句话：把“前端可用的模型列表”先存一份本地和云端快照，避免页面每次打开都去实时请求供应商接口。

具体有这几个作用：

1. 提升页面打开速度  
API 配置页和模型相关页面先读本地缓存，不需要每次现查供应商 `/models`，页面能更快渲染。

2. 降低对供应商接口的依赖  
供应商接口可能慢、限流、失败、返回不稳定。缓存让前端运行时不直接依赖这些外部接口，减少抖动。

3. 作为同步数据的一部分跨设备共享  
模型缓存会进入 `app-config` / `access-control` 的云端快照，同步后别的设备也能拿到同一份模型结果，不用每台设备都重新拉一次。

4. 保存“已经归一化过”的模型结果  
服务端会先把不同供应商返回的数据整理成统一结构，再写入缓存。前端读缓存时不需要自己适配各家格式。

5. 支撑派生字段展示  
像 `cachedModels`、`modelCount` 这类字段就是缓存结果，前端可以直接显示模型数量、模型列表等信息。

按当前实现，模型缓存不是“真实来源”，真实来源还是供应商 API；但页面运行时主要依赖缓存。流程是：

供应商 API -> 服务端拉取和归一化 -> 写入 PostgreSQL `model_catalog` 和 `sync_artifacts` -> 前端下次校验到版本变化后同步到本地缓存

所以它本质上是“模型目录的加速层 + 同步快照层 + 容错层”。

模型数据更新什么时候更新


## 🤖 Assistant (2026-03-18 05:07:06 UTC)

模型数据不是实时更新的，按当前机制主要在这几种时机更新：

1. 你点击“保存并同步”时  
这是前端最明确的触发点。`API 配置页`不会在打开页面时自动刷新模型，而是在你点击“保存并同步”后，才会触发数据库同步和模型刷新流程。这个在 `docs/db/data-storage-sync-matrix.md` 里写得很明确：页面打开只展示本地缓存，模型刷新只在“保存并同步”时触发。

2. 后台脚本主动刷新时  
服务端可以通过脚本 `scripts/refresh-provider-models.ts` 手动拉取各供应商模型，再写入 PostgreSQL 的 `model_catalog` 和同步快照。这属于运维/后台触发，不依赖前端页面。

3. 调用受控接口时  
可以通过 `POST /api/db/models/refresh` 触发模型刷新。接口会从供应商拉取模型，归一化后写回云端。如果配置了 `MODEL_SYNC_TOKEN`，还需要带鉴权。

4. 前端下次做版本校验时  
这里要区分“云端更新”和“本地看到更新”不是同一时刻。模型数据在云端被刷新后，前端不会立刻自动拿到，只有在下一次页面加载或同步校验时，发现云端版本变了，才会把新的模型快照同步到本地 `IndexedDB`。

可以把时间线理解成这样：

供应商模型变化
-> 后台脚本 / 刷新接口 / 保存并同步 触发云端刷新
-> PostgreSQL 中的 `model_catalog` 和 `sync_artifacts` 更新
-> 前端下一次页面加载时检查版本
-> 本地模型缓存更新

- 云端更新时间：在“保存并同步”、脚本刷新、接口刷新时

配置和对话不一样，配置的同步策略更偏“明确覆盖”，没有对话那种重点保历史消息的合并逻辑。
